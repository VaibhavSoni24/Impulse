# IMPULSE Candidate Versioning & Registry Architecture

## 1. Overview & Purpose
Stage 43 establishes a deterministic, immutable candidate registry and provenance system for IMPULSE. Every candidate software engineering agent configuration—spanning prompts, tools, retrieval mechanisms, test strategies, recovery loops, specialist topologies, and adapters—is explicitly versioned, tracked, and cryptographically verified.

> [!IMPORTANT]
> **Provenance Guarantee:** A candidate must be 100% reconstructable from its manifest. No agent configuration can be promoted without verifiable evidence and a reproducible Git commit hash.

---

## 2. Canonical Naming Vocabulary
IMPULSE employs a structured, human-readable vocabulary:
- **`E0`**: Minimal root agent baseline (`impulse_e0_baseline`).
- **`E1`**: Prompt evidence discipline (Step 5 root cause hypothesis requirement).
- **`E2`**: Structured task state observation.
- **`R1`**: Semantic code retrieval (lexical + embedding hybrid).
- **`R2`**: Semantic + dependency graph retrieval.
- **`D1`**: Debugger recovery specialist.
- **`S1`**: Scout localization specialist.
- **`V1`**: Reviewer pre-submission validator.
- **`C1`**: Context compaction and window optimization.
- **`M0`–`M5`**: Frozen competition topology candidates (Stage 24 baselines).
- **`L1`**: LoRA tool-discipline adapter candidate (currently `BLOCKED`).
- **`RC1`**: Release candidate identifier (currently `RESERVED`).

Timestamp-only identifiers are strictly forbidden. Identifiers are explicit, canonical, and permanent.

---

## 3. The Immutability Law
> **Once candidate identifier X refers to behavior/configuration Y, X MUST NEVER later refer to behavior/configuration Z.**

- If runtime behavior or configuration changes, a new candidate ID must be created.
- Finalized candidate manifests cannot be modified in place.
- Non-behavioral metadata corrections increment semantic patch versions (e.g. `1.0.0` -> `1.0.1`), never mutating the candidate's operational identity.

---

## 4. Lineage & Single-Variable Discipline
Every candidate records its direct parent in `parent_candidate_id`:
- `E1` -> `E0`
- `E2` -> `E1`
- `R1` -> `E2`
- `R2` -> `R1`
- `D1` -> `E2`
- `S1` -> `E2`
- `V1` -> `E2`
- `M0` -> `E0`
- `M1`–`M5` -> `M0`
- `L1` -> `M0`
- `RC1` -> `M0`

### Change Contract
Each candidate must declare exactly **one** primary experimental dimension (`baseline`, `prompt`, `state`, `retrieval`, `testing`, `recovery`, `topology`, `skill`, `adapter`, `multi_adapter`, `packaging`, `combined_ablation`).

If more than one major dimension is altered simultaneously, the comparison engine (`scripts/compare_candidates.py`) flags a `MULTI_DIMENSION_EXPERIMENT` warning to prevent unscientific confounders.

---

## 5. Candidate vs Run Separation
- **Candidate:** The invariant definition of the architecture, prompt, tools, skills, and configuration under evaluation.
- **Run:** A single execution instance of a candidate in a specific compute environment (e.g. `LOCAL_CPU`, `KAGGLE_FREE_GPU`).

Multiple runs aggregate under one candidate without overwriting raw run traces. Candidate identity remains completely invariant across different compute environments.

---

## 6. Evidence Modes & Promotion Discipline
Every candidate manifest records an `evidence_mode`:
- **`LIVE`**: Empirical benchmark execution traces with verified metrics.
- **`FIXTURE`**: Verification traces generated by test fixtures (strictly forbidden from production promotion).
- **`INFRASTRUCTURE_ONLY`**: Plumbing and validator verifications without live inference.
- **`UNAVAILABLE`**: Pending or blocked execution.

### Promotion Rules
Candidate lifecycle status (`VALIDATED`, `SMOKE_PASSED`, `CONFIGURED`) is strictly separated from promotion status (`NOT_PROMOTED`, `PROMOTED`, `REJECTED`):
- A candidate may be valid without being selected as the current best.
- Promotion strictly requires `LIVE` evidence, clean-copy verification, and zero held-out regression.

---

## 7. Current-Best Pointer
The active production candidate is tracked in `experiments/candidates/current_best.json`. It points exclusively to a genuinely validated candidate passing all submission validator checks (`M0`). It is never set to hypothetical, blocked, or unverified candidates.

---

## 8. Special Candidate Rules
- **L1 (LoRA-v1):** Remains in status `BLOCKED` and `promotion_status: BLOCKED`. Current repository has zero adapter weights and no executed Stage 40 A/B ablation.
- **RC1 (Release Candidate):** Remains in status `RESERVED` and `promotion_status: RESERVED` until Stage 50 final candidate evaluation formally selects the winning candidate.

---

## 9. CLI Tools
```bash
# Validate all registered candidate manifests
python scripts/validate_candidate.py --all

# Compare two candidates and inspect deltas
python scripts/compare_candidates.py E0 E1

# Inspect complete lineage tree from root
python scripts/compare_candidates.py --lineage E0

# Register a new candidate
python scripts/register_candidate.py --id E3 --parent E2 --dimension prompt --description "Prompt hypothesis v3"
```
